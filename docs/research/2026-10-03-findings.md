## Confirmed requirements

- Product: VibeShell. Simulated system identity: VibeOS.
- A familiar GNU/Hurd-style terminal experience with plausible Unix behavior, branded VibeOS/VibeShell.
- Shell/system effects are simulated, including apparent network operations, package installations, and language interpreters. The later user instruction permits generated persistent application logic inside a suitable sandbox.
- Any invented program or unexplored file/folder must be capable of receiving a plausible AI-generated presentation. Applications may be created, retained, and extended on demand; a fixed command catalogue is insufficient.
- The application core must not depend on a transport. SSH ships first; a local stdin/stdout adapter comes later.
- Ordinary SSH clients must work. Public mode accepts any username without a password. Secure mode accepts only configured users with a valid password checked against a hash file. Client public-key/certificate login is out of scope.
- Public usernames intentionally identify shared, resumable histories/worlds; anyone may claim the same public username.
- Persistent private user worlds and a persistent shared world are both required. Cross-user sharing can be disabled by configuration. When enabled, the agent chooses how to combine these scopes.
- The agent understands Unix/Hurd home-directory conventions and can decide simulated access to another user's home. Simulated access rules are part of the experiment; they are distinct from actual access to service credentials and infrastructure.
- Multiple simultaneous sessions for one user must share exact persistent facts and file contents.
- Full-screen interactive programs, including vi, less, and top, are required in v1. Generic cursor/editing/scrolling/rendering operations can run locally; these named programs are examples rather than the complete application set.
- OpenCode supplies the model API. A suitable independent application/agent runtime is to be selected.
- OpenCode Go support is required in addition to the previously requested free/paid tier configuration.
- More than one API key/account is required in v1. Additional API providers must be possible later.
- Model tiers are ordered. Select randomly within the first usable tier at connection time, keep the selection for the session unless it fails, then exhaust the same tier before advancing. Unavailable models must become eligible again after defined retries.
- Support an automatic suitable-free-model option; use OpenCode's `-free` suffix as a discovery signal, while checking suitability.
- Store every session permanently and support agent retrieval scoped to the session, user, and optionally other users, plus easy full-transcript export.
- Develop in Podman from the beginning, install nothing on the host, and deploy in a Podman/Docker-compatible container exposing one SSH port.
- Break implementation into independently reviewable tasks suitable for multiple AI agents working in parallel. Each subagent must use a dedicated Git worktree and container; the main agent merges the changes.
- Design for approximately 100 concurrent users, with configurable resource/spending controls and no specified fixed monetary ceiling.
- Export full research records, readable transcripts, and terminal replay, excluding actual authentication/API secrets.
- Generate a fresh MOTD per session from a default administrator-configurable prompt.

## VibeOS reference inspection

Repository: <https://github.com/caffeinum/vibeOS>

Checked-out revision: `95b27a8159b1eb89f24da0798b1f6ae8a3fc9328`.

The current site describes a real runtime with AI-generated applications: <https://vibeos.sh/>. The repository contains a Next.js/container implementation and a browser implementation with a v86 Linux VM. VibeShell's wholly simulated command semantics differ from that implementation.

Inspected files and useful observations:

- `src/server/api/routers/terminal.ts`: directly invokes `child_process.exec` on supplied commands. This is not appropriate for VibeShell's simulated command path.
- `src/app/api/chat/route.ts`: integrates a coding-agent SDK, streams output, and enables permission bypass. These execution privileges do not belong in VibeShell.
- `web/README.md`: explains real VM state, workspace persistence, generated browser applications/scripts, and synchronization.
- `web/kernel/agent.js`: has a bounded history window, model adapters, typed tool schemas, tool-result validation, and mechanisms to refresh remembered file information after changes. These are useful concepts; its actual execution powers and browser-specific architecture are not the target.
- `web/kernel/workspace.js`: even rejects generated fake terminals because the reference project expects a real VM. This reinforces that inspiration should not mean inheriting its terminal implementation.
- `LICENSE`: MIT, copyright 2026 Aleksey Bykhun. Preserve attribution and license notices if code is eventually reused. No reference code has been copied into VibeShell application source.

## OpenCode APIs

The originally linked [V2 API reference](https://opencode.ai/v2/docs/api) describes OpenCode server operations, including sessions and local runtime facilities. The [Console Inference API](https://opencode.ai/v2/docs/console/inference/) supplies hosted model inference usable by an independent client.

The [OpenCode Go documentation](https://opencode.ai/docs/go/) supplies separate subscription endpoints. The [V2 Go documentation](https://opencode.ai/v2/docs/console/go) is also relevant. Treat product route and wire protocol separately from model name and credential account.

Observed routes:

| Product/interface | Catalogue | Inference families |
| --- | --- | --- |
| Console inference | `https://opencode.ai/inference/v1/models` | OpenAI-compatible Chat Completions and Responses, Anthropic-compatible Messages, Gemini-compatible generation |
| Console/Zen compatibility URLs | `https://opencode.ai/zen/v1/models` | Protocol-specific suffixes beneath the documented Zen base |
| OpenCode Go | `https://opencode.ai/zen/go/v1/models` | Protocol-specific suffixes beneath the Go base, selected by model |

Do not silently route a Go model to the Console pay-as-you-go endpoint: the same model name can refer to a different allowance or billing route. The provider's optional Go balance fallback also matters when defining application spending limits.

Go documents a product-specific client user agent and a stable `x-opencode-session` header. Its intended traffic is coding-agent traffic; whether a public shell simulation is accepted operationally is not established merely by these documents. Use an honest VibeShell client identity and validate the actual integration with credentials during an explicit experiment.

No authenticated Go test has been performed. A key is needed for that test, supplied through a local secret file or container environment rather than chat or committed source.

### Catalogue observations

- The live Console catalogue returned 82 records; the live Go catalogue returned 43 records.
- Both live responses contained `id`, `object`, `created`, and `owned_by`; they did not provide pricing, tool capabilities, context size, or protocol mappings in the observed payloads.
- Go contained `space-bunny-free` and `longcat-2.5-preview-free`.
- Console contained several `-free` IDs. The list also contained `jev-1.13-free`, which is documented as a structured decision model rather than a shell text generator. Suffix matching is insufficient for suitability.
- Console also listed `big-pickle`, documented as free despite not ending in `-free`; explicitly named models can cover such exceptions.
- The [Models.dev project](https://github.com/anomalyco/models.dev) provides metadata from `https://models.dev/api.json`, including `opencode` and `opencode-go` records. Observed metadata included costs, text modalities, tool support, context/output limits, and some per-model protocol overrides.
- Model metadata is supplementary, not proof of live availability or account entitlement. Match it to the appropriate provider/product; do not infer a Go charge from another route's price or infer free access from missing pricing.
- Keep catalogue refresh, model suitability, account availability, and model health as separate concepts. Unknown metadata should be explicit and allow operator overrides rather than silently interpreting unknown cost as zero.

Source documents: [Console inference](https://opencode.ai/v2/docs/console/inference/), [Console models](https://opencode.ai/v2/docs/console/models/), [Go](https://opencode.ai/docs/go/), [Models.dev](https://models.dev/).

## Candidate implementation choices

These were the initial candidates. PLAN.md records the final selected direction and the qualification tasks that remain before implementation.

### Go and an application-owned agent loop

A Go application with module path `j0s.at/vibeshell` is the leading choice: it fits SSH serving, connection lifecycle control, concurrency, a standalone executable, and container deployment. Normal Go package names should stay short and lowercase instead of reproducing reverse-domain Java package trees.

Go's [SSH package](https://pkg.go.dev/golang.org/x/crypto/ssh) exposes both unauthenticated and password callbacks, SSH channels, and PTY/session primitives. The application must still implement and test channel policy, window resizing, cancellation, and session cleanup. SSH server host keys remain necessary even when client-key authentication is disabled.

Higher-level candidates: [Charm SSH](https://github.com/charmbracelet/ssh), [Bubble Tea](https://github.com/charmbracelet/bubbletea), [Ultraviolet](https://github.com/charmbracelet/ultraviolet), and [ANSI helpers](https://github.com/charmbracelet/x/tree/main/ansi). Full-screen support means `x/term` line reading alone will not suffice. Inspect stream/terminal ownership carefully before choosing a framework; many terminal abstractions assume local file descriptors or a single process terminal.

Alternatives examined: Python [AsyncSSH](https://asyncssh.readthedocs.io/en/latest/) offers a comprehensive asynchronous SSH server; TypeScript [ssh2](https://github.com/mscdex/ssh2) pairs naturally with JS model SDKs. The final choice should be explained against these alternatives rather than inherited from VibeOS or the source CLAUDE.md.

### Persistence and retrieval

SQLite is a candidate for a single application instance, subject to target concurrency and storage requirements. [FTS5](https://www.sqlite.org/fts5.html) supports transcript full-text search, and [WAL](https://www.sqlite.org/wal.html) allows concurrent reads while writes are serialized. WAL has one writer at a time and requires local-machine storage; put the database on a Podman named volume rather than a network share. The [modernc SQLite driver](https://pkg.go.dev/modernc.org/sqlite) is a candidate for a Go implementation.

Historical evidence and current world state serve different purposes:

- Append-only session events preserve the research record.
- Transactional world state preserves exact current facts/files.
- Search indexes and summaries accelerate retrieval but are derived and must not replace raw events.
- Exact command/path lookup needs dedicated structured indexes alongside full-text search, especially for paths containing punctuation and for matching `/some` against `/some/place` at path boundaries.
- A historical listing is evidence of what was emitted then, not automatically the current contents after another session has changed a file.

Concurrent sessions require versioned changes and conflict handling. Model generation should operate on a captured state version, then commit accepted changes atomically; no database transaction should remain open for the whole remote model call.

### Routing and failure handling

The routing domain should distinguish provider, product, model, account/quota group, and key. Multiple keys for the same account do not imply independent allowances. An invalid key, model removal, account quota, provider outage, and request-specific context error should not all disable the same global resource.

Separate provider retries from tier failover so retries cannot multiply silently. Preserve the session's canonical context across model changes. Record attempted routes, errors, timing, and accepted output for research without recording secrets.

Full-screen redraws and streamed output need explicit commit points. A replacement model must not silently regenerate output already emitted to the terminal, and simulated mutations must not be applied twice after retry. These are implementation-plan topics that remain relevant regardless of the selected language.

## Final clarifications and generated-app research

The user selected local responsive terminal primitives, GNU/Hurd appearance with plausible Unix behavior, SSH-only v1, full research exports, and an AI-generated configurable MOTD. Capacity planning should assume around 100 users; exact limits remain configurable. The later instruction explicitly requires arbitrary invented programs/files/folders and allows generating/extending persistent apps if that is the better implementation.

The selected direction is therefore a Go host, persistent generated JavaScript application artifacts, and a restricted QuickJS/Wasm engine, while all filesystem/process/network effects remain inside the simulated world. This avoids a model call for every key and preserves extensible behavior without requiring a full Linux VM per user.

Sources inspected: [wazero](https://wazero.io/), [wazero runtime configuration](https://pkg.go.dev/github.com/tetratelabs/wazero), [QuickJS](https://bellard.org/quickjs/quickjs.html), [fastschema/qjs](https://github.com/fastschema/qjs), and [Javy](https://github.com/bytecodealliance/javy).

The qjs adapter was cloned via Podman into `.research/qjs` at revision `461716f4f380f81ffd09378751f1812919cddbca`. Its `runtime.go` creates a WASI filesystem configuration with `WithDirMount(runtime.option.CWD, "/")`; its default options resolve CWD from the process. That default is unsuitable for VibeShell. The plan requires a capability-free bridge with explicit memory/time/output limits and no actual directory mounts, environmental secrets, network, process execution, or unrestricted Go proxies.

This was source review, not a sandbox benchmark or penetration-test result. The plan includes a bounded container-only qualification task and does not assert that the stock library is safe for this application.

Additional primary references: [asciicast v2 event/replay format](https://docs.asciinema.org/manual/asciicast/v2/), [SQLite consistent backup API](https://www.sqlite.org/backup.html), and [Go Argon2 implementation](https://pkg.go.dev/golang.org/x/crypto/argon2).

No product questions remain pending. Authenticated Go tests still require a locally supplied API key; library execution/performance qualification belongs to the first implementation experiments. The completed plan includes those gates, state/event contracts, configuration, container workflow, and independently owned parallel-agent tasks.
