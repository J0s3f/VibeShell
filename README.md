# VibeShell

VibeShell is a research prototype of a Unix-like shell whose entire world —
filesystem, programs, and file contents — is **generated by language models and
executed only inside a bounded sandbox**. It never runs a real program, never
touches the host filesystem or network, and never hands user input or generated
code to a real shell.

The system presents itself as **VibeOS** with the **VibeShell** shell, reachable
over a real SSH connection.

> This is a simulated environment. Apparent commands, files, processes, and
> network operations are simulated; nothing runs on the host.

## The idea

- You type a command. A shell builtin (`ls`, `cat`, `cd`, `pwd`, `mkdir`, `touch`,
  `rm`, …) runs against a durable, per-user simulated filesystem.
- An unknown command is written by a language model as a small JavaScript
  program, staging-validated, activated, and executed in a Wasm sandbox.
- A path that does not exist yet is *materialized* on demand with plausible
  AI-generated content and then persists.
- Models are reached through provider adapters (direct HTTP and the OpenCode CLI)
  behind routing, health, and failover.

## Safety model

- Generated code runs only inside `internal/adapters/sandbox` (QuickJS/Wasm on
  `wazero`) with no host filesystem, network, environment, process, or native
  module access.
- Terminal control sequences are owned by a trusted screen model; text shown as
  data can never activate clipboard, hyperlink, or title-change controls.
- Shell and system effects are entirely simulated. Network commands remain
  simulated.

## Architecture (hexagonal)

Dependencies point inward: adapters depend on application ports and the domain;
the domain depends on nothing outward.

| Layer | Packages |
| --- | --- |
| Domain | `internal/domain` — identities, invariants, policies, state transitions |
| Ports | `internal/ports` — inbound/outbound interfaces |
| Application | `internal/application` — sessions, turns, commit, admission |
| Adapters | `internal/adapters/{ssh,sqlite,sandbox,opencode,opencodecli,config}` |
| Capabilities | `internal/{routing,simulation,presentation,terminal,apps,discovery,inference,provider}` |
| Composition | `cmd/vibeshell` — dependency wiring, CLI, SSH handler |

## Build and run (container-only)

Development happens inside a Podman container; no language, package manager, or
project dependency is installed on the host.

```powershell
scripts/dev.ps1 image     # build the pinned dev toolchain image
scripts/dev.ps1 start     # create/start this checkout's container
scripts/dev.ps1 test      # go test -race ./...
scripts/dev.ps1 status    # container, volumes, published SSH port
```

The service is configured by a validated JSON document (see
[`examples/vibeshell.json`](examples/vibeshell.json) and
[docs/guides/configuration.md](docs/guides/configuration.md)) and exposes a
single SSH port. Live provider tests are opt-in and credentialed; the routine
suite is offline.

## Run the published image

Released images are published to the GitHub Container Registry for
`linux/amd64` and `linux/arm64` when a `v*` release tag is pushed. Pull and run
the service with the configuration mounted from a file and persistent state in a
volume:

```sh
docker pull ghcr.io/j0s3f/vibeshell:latest

docker run --name vibeshell \
  -p 2222:2222 \
  -v "$PWD/vibeshell.json:/etc/vibeshell/vibeshell.json:ro" \
  -v vibeshell-state:/var/lib/vibeshell \
  ghcr.io/j0s3f/vibeshell:latest
```

Then connect with any SSH client:

```sh
ssh -p 2222 alice@127.0.0.1
```

- **Configuration** is a single strict JSON file mounted read-only at
  `/etc/vibeshell/vibeshell.json` (the service's default path). The image ships a
  working default there; mount your own to override it. See
  [`examples/vibeshell.container.json`](examples/vibeshell.container.json) for the
  shipped default and [`examples/vibeshell.json`](examples/vibeshell.json) for a
  fuller example with model providers. The configuration is validated before the
  service starts; an invalid file fails startup with actionable errors.
- **Persistent state** (the simulated world, generated applications, and the SSH
  host key) lives in the named volume mounted at `/var/lib/vibeshell`. Keep the
  volume across restarts to keep the world; delete it for a fresh one.
- **Prompts** ship at `/etc/vibeshell/prompts`; mount your own over that
  directory to change presentation. Relative prompt paths in the configuration
  resolve against `/etc/vibeshell`.
- **Model providers are optional.** With no configured account the shell and its
  simulated filesystem still work, while the MOTD and generated applications
  report a truthful unavailable message. To enable them, add `providers`,
  `routes`, `accounts`, and `tiers` to your configuration and supply the key as
  an environment secret, for example
  `-e VIBESHELL_OPENCODE_KEY=...` with
  `"secret_ref": "{env:VIBESHELL_OPENCODE_KEY}"`.
- The shipped default uses `auth.mode: "public"` (any username, no password) and
  publishes a single port, `2222`. For a shared deployment switch to
  `"secure"` with a password file, and never expose more than the SSH port.

To build the same image locally (Podman or Docker):

```sh
podman build -f containers/Containerfile --target runtime -t vibeshell .
```

## Testing

```powershell
scripts/dev.ps1 test
```

The repository contains unit, contract, integration, end-to-end, and load
suites, plus fuzz tests for the terminal input decoder and screen model.
